## 1. 原厂接口与当前支持

| 原厂约定 | 项目当前行为 | 待验证事项 |
|---|---|---|
| 视频 `http://<IP>:81/stream` | 电脑识别接入层可读取网络视频源 | 实物图传与长时间重连 |
| TCP 8888 数据透传 | 原厂资料描述此端口；当前电脑看板不连接它 | 实物正常模式下是否开放及透传方向 |
| WebSocket 2080，路径 `/ws` | 原厂资料描述此接口；当前电脑看板不连接它 | 固件版本、接口和访问控制 |
| `$A角度#`，三位数字，上下舵机 | A 映射 TILT，STM32 PA7/TIM3_CH2 | 实际俯仰安装方向和限位 |
| `$B角度#`，三位数字，左右舵机 | B 映射 PAN，STM32 PA6/TIM3_CH1 | 实际水平安装方向和限位 |
| `$7,0,0,0#`，停止 | 与 `$STOP#` 同样进入独立停止优先通道，清空排队动作 | APP 按钮至物理输出关闭的延迟 |
| 小车前进、后退、转向等 `$1...#` 至 `$6...#` | 不解释为摇摆或安抚，应用拒绝 | 本项目不沿用小车动作语义 |
| USART 115200，无奇偶校验，无流控，1 位停止位 | STM32 USART3 为 115200；配置命令不附加新行 | 同版固件的接收、返回与复位时间 |
| `sta_ip`、`ap_ip`、`wifi_ver` | 固件定期查询 IP；版本需台架读取记录 | IP 可用不代表图像检测成功 |

A/B 映射已按原厂《APP通讯协议.pdf》第 1 页修正。旧版工程说明将 A/B 解释相反，不能再据此接线。舵机逻辑索引仍为 0=PAN、1=TILT；协议字符与索引不是按字母递增对应。

连续 A/B 指令保留另一轴未完成的目标；角度仍经过 PAN 60–120°、TILT 75–105° 的临时软限位和分步运动。TILT 的反向配置独立于 A/B 映射。台架必须验证物理方向，不能通过交换电源线来改方向。

## 2. 资料包原理图的四针接口

《原理图/ESP32-CAM-原理图.pdf》标注 YB-MEV02-V1.0，主模块为 ESP32-S3-WROOM-1U-N4R2。J4 为 PH2.0-4P，网名如下；这不是所有叫 ESP32-CAM 的板卡的通用针序。

| J4 针号 | 原理图网名 | 同版板卡的项目连接 |
|---|---|---|
| 1 | RXD0，经 R14 22R | STM32 PD8/USART3_TX |
| 2 | TXD0，经 R29 22R | STM32 PD9/USART3_RX |
| 3 | GND | 公共地 |
| 4 | 5V | 独立稳定且额定满足模块要求的 5V 支路 |

必须先核对实物丝印、连接器 1 脚方向和板卡版本。不能按线色或插头观察方向猜针号；5V 是此图的供电网名，不是 UART 高电平允许值。原理图的串口网连接 MCU RXD0/TXD0，不是 GPIO35/36 的 UART1。

## 3. 为什么不能直接把 AI 示例当作出厂固件

已核对的源码位于：

`C:/baidunetdiskdownload/ESP32图传模块/1.esp32摄像头AI单例源码/3.AI单例教程源码/AI_Human_Face_Recognition/AI_Human_Face_Recognition/esp32Board_wifi/main`。

- `include/my_usart.h` 使用 UART0，TX=GPIO43、RX=GPIO44。
- `include/my_usart1_user.h` 使用 UART1，TX=GPIO36、RX=GPIO35；这与上述 J4 的 UART0 不是同一接口。
- `src/my_usart1_user.c` 接收 UART1 的 `sta_ip/ap_ip` 后调用 `Uart_Send_Data()` 返回至 UART0，而部分按键命令调用 `Uart1_Send_Data()` 返回 UART1。若实物烧录同一源码且主控接 UART1，可能出现查询回复跑到另一串口的问题；不能据此推断出厂二进制也有同样问题。
- 原厂串口协议明确提示 AI_MODE=4 人脸识别模式会失去 Type-C 串口配置及网络透传功能。当前项目选择正常模式 0，不应为了取得视频盲目刷入人脸识别示例。

当前 STM32 的 ESP32 配置步骤要求“UART 发送完成 + 独立一行 OK”。应答从发送开始计时，3 s 内未收到有效应答则停止本轮配置；收到 `fail`/`fail,...` 或 RX 错误也停止。ACK 在发送完成回调前到达仍会保留，但达到截止时刻的应答不采纳；ISR 记录应答到达时间，不用主循环消费时间把迟到应答变新。配置期间禁止交叉发送 IP 查询。

只有发送尚未启动成功时才会进行最多 3 次重试；在途超时、部分发送或应答丢失时不重放可能已生效的配置。取消发送失败时仍保留在途缓冲区，不能重新初始化覆盖它。成功后记录 `esp_cfg_result=2`，仅表示本轮六条命令分别收到应答，不证明断电保存、网络连通或视频正常。

原厂资料只描述 OK/fail 信息，未明确完整帧终止方式。当前严格按换行结束的独立应答解析，裸 `OK`、包含 OK 的其它文本、隐藏 NUL 和超长行都不能作为成功确认。若实物输出不带换行，需要先抓取原始返回后制定可靠边界；不根据未经验证的空闲间隔猜测成功。

原厂 OK 不含命令序号，也不是认证信息。已收到但明显迟到的应答会被拒绝，但跨步骤延迟重复包仍不能像带序号协议一样可靠关联；最终双向通信仍需命令 ID、去重、过期、访问控制和配置读回。`esp_cfg_fail=0` 不能代替这些证据。

| 日志 `esp_cfg_result` | 含义 |
|---|---|
| 0 | 未启动配置 |
| 1 | 进行中，可能正在发送、等应答或等模块复位 |
| 2 | 六步均获应答，仍需实际配置读回与视频检查 |
| 3 | 发送启动或在途发送失败 |
| 4 | 应答缺失或迟于 3 s 截止 |
| 5 | 模块明确拒绝 |
| 6 | 本地参数/报文容量错误 |
| 7 | 接收错误，应答不可采信 |

`esp_cfg_ack_timeout` 与 `esp_cfg_reject` 为累计计数，`esp_cfg_fail` 仍保留便于兼容既有日志处理。不要把“进行中”或失败后 IP 可用解释为配置成功。

## 4. 下一步联调顺序

1. 拍照确认板卡与 J4 1 脚、逻辑电平、供电入口；保持电机与舵机断能，仅接图传和主控通信。
2. 记录串口 `wifi_ver`、`ap_ip/sta_ip` 的原始返回；确认正常模式、视频地址及透传接口。不要先发 `wifi_reset`，以免覆盖已有网络配置。
3. 在授权的隔离局域网验证透传：先 STOP，再验证 A/B 两轴的实际方向。脱载或固定机构后才能使能 PWM，并测量停止响应及供电跌落。
4. 确认物理协议后接入配置 OK/失败应答、命令序号、去重、过期和执行结果；加入认证和权限。原厂透传端口不等于已认证接口，不开放公网控制。
5. 接入电脑只读遥测与视频，记录断流、断串口、恢复、告警和数据年龄；随后开展背景负样本评估和带载长稳测试。
