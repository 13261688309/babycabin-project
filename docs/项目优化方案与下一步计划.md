### P1：提升持续运行稳定性和控制一致性

1. **逐步消除阻塞。** ESP32 初始化中的固定延时，加上调用方延时，累计约 10.7 秒，期间尚未进入主循环。先保证本地监测和停止逻辑可调度，再用状态机完成 ESP32 配置、等待、重试和退避。DHT11 的约 21 ms 起始等待分阶段执行，位读取时序单独测量。日志使用有界发送队列，避免通信拖慢控制。
2. **串口接收可靠化。** 先为现有中断接收补齐 ORE/FE/NE 等错误恢复、短帧超时、严格长度校验和有界消息队列；记录溢出次数。需要提高吞吐时再迁移到 DMA/IDLE；迁移时验证 H743 的 DMA 可访问内存、缓存一致性及缓冲区生命周期。
3. **统一命令仲裁。** 保留 `BabyCare_Task()` 作为当前运行入口，逐步复用 BabyCabin 服务。设备模式与被观测状态可分开表示，但执行机构只能有一个控制者，不能直接同时启用两套完整 app。优先级建议：硬件急停/故障 > 软件停止 > 人工控制 > 自动安抚；普通语音和 APP 命令按明确的所有权和时限仲裁。
4. **接通真实通信路径。** 当前 `REPORT/ALERT` 发往 USART1 调试口，`bsp_hal_poll_command_packet()` 返回 false。先确定 ESP32 能接收的协议，建立双向遥测/命令通路；增加版本、序号、应答、过期时间、重试和重复命令处理。停止命令可重复执行，启动命令不得因重试延长运行。
5. **严格解析与故障恢复。** 替换 JSON 子串匹配为有界结构化解析；验证命令名、参数类型、范围、时长及报文完整性。心跳过期清除在线状态；检查 HAL 返回值并记录失败。调度消除长阻塞后加入看门狗，按关键任务健康状态喂狗，保存复位原因。
6. **硬件联调。** 确认主控板、语音、ESP32、舵机、电机驱动的实际型号与供电入口；核对共地和逻辑电平，测量电机启动/换向时的电压跌落。依据实际机构设置行程、速度和电流保护，安排独立于网络命令的停止手段。

### P2：形成一个有数据支撑的 AI 和交互闭环

先选择一个场景，例如哭声事件识别或相机目标/在床状态检测。硬件与数据具备哪一种，就先完成哪一种。声强阈值只用于声音事件，不能直接等同于哭声识别。

- STM32 负责采集管理、控制约束、执行与故障处理；ESP32 负责网络和图像传输。识别先在具备数据与算力的平台验证，再评估迁移成本。
- 识别结果必须带来源、时间戳/数据年龄、类别、置信度和模型版本；过期或低置信度结果不启动自动动作。
- 采集不同噪声、距离、光照、遮挡和空床场景；按婴儿/录制会话或场景分组划分数据，避免相邻片段同时进入训练与测试。
- 第一阶段策略使用可解释规则，记录触发原因、动作时长、退出条件和执行前后状态。舒适度评分后置，先验证各输入是否可靠。
- 家长端先做温湿度、连接/传感器健康、当前动作、告警记录、手动停止和命令结果。视频和历史曲线按带宽与时间安排；远程控制接入时同步处理认证与权限。
- 扩展传感器按功能需要逐项接入。每项完成供电/接口确认、驱动、健康状态、故障测试和协议字段后，才开启相应配置开关。

近期第一批实施任务建议控制在以下范围，方便独立审查和回归：

1. 验证 `device_protocol_encode_snapshot()` 的常态、失败态和边界长度，修正整条发送链路容量与截断处理。
2. 修正桥接快照语义，状态机在禁用、失败、过期输入下返回数据不足或对应故障，禁止把默认零值当作安静/正常。
3. 在 `baby_care_app.c` 建立统一停止/故障门禁，先校验命令再改变模式，覆盖 ALERT 下的远程云台命令与最长动作时间。
4. 在工程副本同步 `.ioc`，核实 USART2 波特率，保存可构建基线。

上述任务完成后，再拆分非阻塞启动和串口队列改造，便于定位行为变化。

## 4. 建议验收指标

以下数字是首轮台架目标。机械停止时间、动作幅度和电机保护参数须按实物测量确定，不能由软件目标代替。

| 指标 | 初始目标 | 测量方法 |
|---|---|---|
| 软件停止响应 | 从完整有效 STOP 帧接收完成到输出禁止 ≤100 ms | GPIO 标记配合逻辑分析仪；覆盖采样、日志和联网同时运行 |
| 无效数据处理 | 禁用/失败/过期数据均不触发正常、睡眠或自动安抚结论 | 主机状态机用例和实物拔插/超时注入 |
| 报文完整性 | 所有支持的字段边界组合均不截断，不发送半包 JSON | 协议边界用例、串口抓包和 JSON 解析验证 |
| 命令处理 | 约定速率内连续 1000 帧无非预期丢失或误动作；超载可观测 | 覆盖正常帧、粘包、半包、乱码、重复包和停止优先级 |
| 采集稳定性 | 台架连续采集 1000 次，目标成功率 ≥99%；失败状态正确呈现 | 记录成功、校验失败、超时、连续失败与最后成功时间 |
| 掉线处理 | 心跳过期后及时标记失联；本地停止仍可用 | 断开串口/网络，验证状态过期和重连；超时时间由协议确定 |
| 运行稳定性 | 先 8 小时，再 24 小时，无非预期复位或持续失控输出 | 运行日志、复位原因、队列溢出、任务耗时、电源测量 |
| AI 效果 | 报告 Precision、Recall、混淆矩阵、每小时误报及端到端延迟 | 独立测试集与连续场景测试；目标值在数据基线后确定 |

软件回归重点放在纯逻辑和通信边界：状态转移、输入有效期、命令仲裁、时间计数回绕、协议解析和截断。时序、供电、机械动作和看门狗恢复必须通过实物台架验证。

## 5. 实施前待确认的信息

- 实际硬件型号、语音模块固件协议和 USART2 波特率，以及电机驱动的使能/待机接法。

这些信息影响扩展方案与工期，不影响先完成报文、数据语义和控制门禁的修复。
